Arquitetura do Backend, sprint a sprint

Como o backend do TRAMPO é construído ao longo das 4 sprints — módulos tRPC, tabelas tocadas, integrações externas e jobs. Monolito modular, não microserviços. Otimizado para um dev solo com Claude Code.

Runtime Node.js + Hono API tRPC v11 ORM Prisma DB PostgreSQL + PostGIS Cache/filas Redis (Upstash) Host Railway
01

Visão macro

Uma única aplicação Node (apps/api) servida pelo Hono, expondo um router tRPC. Toda regra de negócio vive numa camada de domínio testável, separada do transporte e do banco. Microserviços ficam fora de discussão: para founder solo, custo operacional não se paga.

Princípio

O backend é um monolito modular. Cada domínio (auth, tasks, payments...) é um módulo isolado com seu próprio router, services e tipos. Eles se comunicam por chamadas diretas de função, não por rede. Se um dia precisar quebrar, a fronteira já está desenhada.

Contrato de exemplo — auth.verifyOtp

Toda procedure valida input com zod. O contexto tRPC carrega o usuário autenticado a partir do JWT já verificado no transporte.

export const authRouter = router({
  verifyOtp: publicProcedure
    .input(z.object({ phone: z.string(), code: z.string().length(6) }))
    .mutation(async ({ input }) => {
      // 1. valida o código no Twilio Verify
      await twilio.checkVerification(input.phone, input.code);
      // 2. cria/retorna sessão Supabase + emite JWT
      return authService.issueSession(input.phone);
    }),
});
LGPD desde o dia 1

CPF entra criptografado (pgcrypto). Documentos de KYC vão para bucket privado, acessados só por signed URL de expiração curta. Nada de documento em URL pública, nunca.

Pricing engine — regras imutáveis no código

O cálculo de preço é domínio puro, sem efeito colateral, 100% testável. As regras de negócio viram constantes em um único lugar.

// valores travados pelas regras de negócio
const MIN_VALUE      = 5000; // R$ 50,00 em centavos
const TASKER_FEE     = 0.15; // comissão tasker
const CLIENT_FEE     = 0.05; // taxa de serviço cliente
const URGENCY_FEE    = 0.30; // + se < 1h

export function quote(baseCents: number, isUrgent: boolean) {
  if (baseCents < MIN_VALUE) throw new DomainError("abaixo do mínimo");
  const base    = isUrgent ? Math.round(baseCents * (1 + URGENCY_FEE)) : baseCents;
  const service = Math.round(base * CLIENT_FEE);   // paga o cliente
  const commission = Math.round(base * TASKER_FEE); // desconta do tasker
  return { base, service, commission, total: base + service };
}
Dinheiro

Tudo em centavos inteiros. Nunca float. Take rate de ~20% sem erro de arredondamento que vira disputa com tasker.

Feed geográfico — query que usa o índice

-- raw query via Prisma; usa o índice GiST, responde em ms
SELECT *, ST_Distance(location, $1) AS dist
FROM tasks
WHERE status = 'open'
  AND ST_DWithin(location, $1, 10000)  -- 10km
ORDER BY dist
LIMIT 50;

Aceite de trampo — lock contra duplo-aceite

Dois taskers clicam "aceitar" no mesmo segundo. Sem lock, o trampo é aceito por dois. A solução é um update condicional dentro de transação: só vence quem encontrar o status ainda open.

async function accept(taskId: string, taskerId: string) {
  return prisma.$transaction(async (tx) => {
    // update condicional: vence quem achar status = 'open'
    const { count } = await tx.task.updateMany({
      where: { id: taskId, status: 'open' },
      data:  { status: 'accepted' },
    });
    if (count === 0) throw new DomainError("trampo já aceito");
    await tx.taskAssignment.create({ data: { taskId, taskerId } });
  });
}

Máquina de estados — transições forçadas

Status nunca é string solta. Cada transição válida é declarada; qualquer outra é rejeitada pelo domínio antes de tocar o banco.

const TRANSITIONS = {
  open:        ['accepted', 'cancelled'],
  accepted:    ['in_progress', 'cancelled'],
  in_progress: ['completed', 'disputed'],
  completed:   ['released', 'disputed'],
};
function assertTransition(from, to) {
  if (!TRANSITIONS[from]?.includes(to))
    throw new DomainError(`transição inválida: ${from} → ${to}`);
}
Regra de integridade

Review só é aceito se existir um trampo concluído entre as duas partes. Sem trampo, sem avaliação — corta avaliação falsa na raiz.

Webhook Asaas — assinatura validada

Roda direto no Hono, fora do tRPC (é um POST externo). Validar a assinatura antes de tudo: um webhook falso de "pago" sem verificação libera serviço sem dinheiro ter entrado.

app.post('/webhooks/asaas', async (c) => {
  const sig = c.req.header('asaas-access-token');
  if (sig !== env.ASAAS_WEBHOOK_TOKEN) return c.text('unauthorized', 401);
  const evt = await c.req.json();
  await paymentService.handleEvent(evt); // idempotente por asaas_id
  return c.text('ok');
});

Escrow — release agendado via fila

Quando o tasker marca "finalizado", o pagamento entra em held e um job é agendado para 1 hora depois. O worker libera o split. Sem cron frágil: fila Redis com delay.

// ao concluir o trampo
await queue.add('escrow-release', { paymentId }, { delay: 3_600_000 });

// worker
worker.process('escrow-release', async ({ paymentId }) => {
  const p = await getPayment(paymentId);
  if (p.status !== 'held') return; // disputado? não libera
  await asaas.releaseSplit(p.asaasId); // repassa ao tasker, retém ~20%
  await setStatus(paymentId, 'released');
});
Janela e multa

Cancelamento grátis até 30 min antes do horário agendado. Depois, multa de 20% calculada no domínio e aplicada via estorno parcial no Asaas. Idempotência por asaas_id impede processar o mesmo evento duas vezes.

Nota sobre IA

Claude API entra como camada de apoio (classificação de categoria, triagem de suporte, pricing dinâmico) — fora do caminho crítico do MVP. Nada de fluxo de dinheiro ou aceite depende de IA. É melhoria pós-beta, não dependência de lançamento.
